    WildINTEL Uploader — User Manual (web)¶

    This manual covers the web interface. What it shares with the command line — installation, the general concepts and the folders it creates — is in the common part; read that first. Part of what the web app does can also be done from a terminal: see the command-line manual.

    1. Getting started¶

    Install the app and run it with no arguments. It starts a small server on your computer and opens the app in your default browser (http://127.0.0.1:8769, or the next free port).

    Info

    Keep the window it opened until you finish — closing it stops the app. Data is kept on your machine; connections to services such as TRAPPER, Epicollect and map providers depend on the features you use.

    The app opens on the welcome screen, which says what it does — from the field to a curated, standard dataset — and gives four points:

    • Validated.
    • Traceable: each deployment is sealed with the checks it passed and a SHA-256 fingerprint of every image.
    • Standard: Camtrap DP fields, all times in UTC.
    • Organized: research project › collection › deployment.

    On the first launch, there are no research projects yet. Press Get started to open Initial setup.

    Initial setup¶

    The assistant asks for the basic data of the research project and, optionally, the people and equipment used in the field. For this example we will create WICP_02, a project with four sites.

    1. The research project — enter its required Acronym, WICP_02, and Name, for example WICP_02 Doñana census. The acronym names its folder. Press Continue.
    2. The trappers — add the people who go to the field, for example Pedro Pérez. Each needs a unique Username and Full name; affiliation and email are optional.
    3. Their roles in the research project — assign roles to the trappers, such as principal investigator, contact or contributor.
    4. The sites — add each location with its Site id, latitude, longitude and Timezone, for example WICP_02_001, 37.0123, -6.4412 and the timezone used by its camera. UTC is the default; for a different timezone, say whether the cameras ignore summer time.
    5. The cameras — add each camera's Label, for example CAM-001; serial number and model are optional.
    6. The SD cards — add each card's Label, for example 1; brand and capacity are optional.
    7. Review — check the summary and press Create it. The project and the other entries are saved at this point, and the app attempts to make the project the default. Check the result for any entries that could not be saved.

    In steps 2–6 you can add entries one by one or use Import from CSV and Download a template. You can also skip them and add them later in Settings › Entities. Project details such as description, keywords and sampling design can be filled in there as well. See Entities and the examples in examples/entities_example/wicp_02.

    New sites are Pending: their first visit starts them, and earlier revisions do not wait for them. The timezone is important for interpreting camera dates and cannot be changed after the site is created; see Locations.

    After setup, choose Register the first visit or return to Main menu. To create another project later, use Create a new research project on the welcome screen or in the research project selector.

    Managing visits¶

    Once the entities are defined, we can start with the visits (see Register the visits). From the menu we press Register the visits, and choose By hand.

    Registering many visits at once

    By hand is the way to register a few visits. To register many at once, the visits can be read from a file instead: with Custom CSV, a CSV of any shape in which we say which column gives each field of a visit, or with WildINTEL Epicollect CSV, the CSV downloaded from the WildINTEL Epicollect project. See Register the visits.

    To register the visit to the first location, pick WICP_02_001 in the form.

    In Who, select the people who went, for example Pedro Pérez. You can search for a trapper by name.

    In When, enter the date and time of the visit. The form also shows the GPS coordinates used to check the location.

    GPS coordinates of the visit

    These coordinates are where you were when you recorded the visit, not the site's coordinates. The app compares them with the selected site's stored coordinates to check that you are nearby. Enter your position or use the Use my current position button. The fields initially contain the site's coordinates, so the initial 0 m match does not confirm where you actually are.

    Next, say what was done: as no camera is known there yet, the visit is an Installation. Open the Camera section and choose the camera that is installed, CAM-001, say that it was calibrated, and give its height, its tilt and its heading and the delay between triggers; in SD card, pick the card that is left in it, the 1.

    We press Review the visit, check what is going to be kept and confirm it.

    Once the visit is registered, we go to the Visit dashboard (see Visit dashboard). The first revision, R0001, has been created and the visit is Deployed: the camera is out. Other pending sites are not yet expected in the revision; their first visits start them. For each planned site shown in the dashboard, press the Create the visit button (:material-map-marker-outline:) at the right of its row to register its visit.

    Continue registering the visits to the other sites. A revision is finished when every expected site has a visit recorded; if a site cannot be visited, it can instead be marked as not visited. The next revision cannot begin until the previous one is finished.

    Once the first revision is finished, we plan the next round of visits (R0002). Some time later, we return to the first site to check the camera and collect its SD card. We register this new visit in the same way, but now the camera is there, so we answer that we see it, and that it is well: the visit is a Revision. The camera is the one the visit before says, so it is not asked; we say that it was calibrated and, in SD card, how many images the card collected has and which card is left, for example 5.

    Once the visit has been registered, the app offers to Import the images collected on the SD card and associate them with the visit in revision R0001. You can import them now or later from the deployments menu.

    Managing deployments¶

    The images on the collected card belong to the deployment associated with the earlier visit, in R0001. The app can import them directly from the SD card or from a folder on your computer.

    For this example, choose No, they are in a folder and select the folder containing the images. The app scans it and shows how many images it found. It also asks which SD card contained them: select the card collected during the visit. The app checks it against the card recorded as left in the camera.

    Press Continue to see the quality checks available for the images and their folder. For each check, choose whether to skip it, run it as a warning that allows you to continue if it fails, or require it to pass before proceeding. Press Run checks to run the selected checks.

    Once the checks are complete and all those set to Must pass have passed, continue to the recording period. This is the period during which the photos were taken. By default, its start and end come from the field visits: R0001, when the SD card was left in the camera, and R0002, when it was collected. The dates can be adjusted with Edit dates without changing the visits.

    After the dates, the app shows deployment details in the Camtrap DP format. Most fields are optional, and the available details are pre-filled with information from the field visit where the SD card was left. You can review or edit them before continuing.

    The app then runs another set of checks on the deployment and the image collection as a whole, rather than examining each image separately. For example, it checks whether the images' dates fit within the deployment's recording period. As before, you choose which checks to run and whether each must pass to continue, or can instead show a warning and let you proceed. The app then imports the images into the collections folder, one collection for each revision. See Import the images and Import deployments for the available import flows.

    Once the checks pass, the app prepares the images before they can be saved:

    • It copies them into the deployment's collection folder; the originals are not changed.
    • It reads each image's capture date and converts it to UTC using the location's timezone settings. If an image has no EXIF date, it uses the file date.
    • It can rename the images using the deployment id and capture date, and resize images wider than the configured maximum width.
    • It can add authorship, rights and license metadata to each image.

    Add metadata. This optional step writes information such as the creator, owner, publisher, rights, license and location into each image as XMP.

    Add metadata

    The notice under What gets written into each image warns when Owner or Publisher has not been set in Settings › Preprocessing. If either is missing, its value will be written as Unknown; the notice does not prevent you from continuing. Set these values in Settings if you want the images to carry the correct attribution. This step also needs ExifTool; if it is unavailable, the app disables the step and explains why.

    When you start preprocessing, the app copies and processes the images. How long this takes depends on the number of images and the processing steps you selected. If everything completes successfully, the app shows a summary of what was done and asks you to confirm saving the deployment in your local collection. Saving seals it so the app can detect later changes.

    Once saving is complete, the app offers the option to upload the deployment to a repository. In this example, the Upload to TRAPPER button sends it to TRAPPER; you can also upload it later.

    Managing uploads¶

    Before uploading to TRAPPER

    Configure and test the connection in Settings › Uploader › TRAPPER before uploading.

    When you press Upload to TRAPPER, the app takes you to the upload form with this deployment already selected. There, choose the TRAPPER classification project to which you want to link the deployment.

    Press Continue. Choose Upload to TRAPPER and select Delete the package files once they are uploaded if you want the generated zip and YAML files (and the deployment's row in the collection CSV) removed after TRAPPER receives them.

    Press Continue to start the upload. The app creates any missing locations and deployments in TRAPPER, then uploads the images. If everything succeeds, it shows a link to the deployment in TRAPPER, where you can view the uploaded images.

    2. Settings¶

    Press ⚙️ Settings. It has its own sections on the left; one Save saves them all, and a red dot marks a section with an invalid value.

    General¶

    • Data folder — where the app keeps what it makes: the collections, the reports and the packages, each in a folder inside it. Blank uses Documents/wildintel-uploader; a path must be absolute (or start with ~).
    • Collections folder, Reports folder and Packages folder — where the collections, the reports of the checks and the packages made to upload to TRAPPER are kept. Blank, each is a folder (collections, reports, packages) inside the data folder; set one to keep it somewhere else, on another disk for instance. A path must be absolute (or start with ~). What is already kept in the old place is not moved: do it by hand.
    • Welcome page — on by default: the page that says what the app does is shown when it opens. Turn it off to open straight on the menu (or on the runs left unfinished); the tick Do not show this page again of the welcome page does the same. The title of the header then goes to the menu.
    • Workers — how many images are validated and preprocessed at once. Up to the number of processors of your machine pays off; the default is that number, up to 4.
    • Log level — how much the app logs (ERROR, WARNING, INFO, DEBUG). At DEBUG it logs every step.
    • Log file — download it, or delete it. It lives in the log folder of your system (~/.local/state/wildintel-uploader/log on Linux), which can't be changed. It rotates at 5 MB keeping the last 5. Attach it to any bug report.

    • About — at the top: the app's name and version, Check for updates (it offers the download when there is a newer version), and links to Report a problem (a GitHub issue that already says the version and your browser), the Documentation, the GitHub project and What's new (the release notes).

    • Keep the seconds in the logs — the start and the end of the deployments written in the FileTimestampLog and the FieldworkLog, for the visits of any origin. Off by default: they are cut to the minute.

    Uploader¶

    The platforms a deployment can be uploaded to, each set up on its own tab. TRAPPER is the only one for now; the section is there so that other platforms can be added in a future version.

    Trapper¶

    Each platform can be used or not — a check at the top of its tab (a green dot on the tab says it is used). One not used is not offered, and has no card in the Uploads dashboard.

    The server's URL, and the username (its email — the TRAPPER import form only accepts that) and password of your account. Test connection reports the research projects it can see. The password is saved in settings.toml but never sent back to your browser.

    Upload packages — Largest package is the size, in MB, of the packages an upload makes: the images of each deployment are uploaded in packages of this size at most (500 by default, up to 5000).

    Agouti¶

    What an upload to Agouti needs: the address of its API (usually https://api.agouti.eu), the API key that Agouti's support gives (kept private, and a blank key on saving keeps the saved one) and the id of the project. Nothing is uploaded to Agouti yet: the form only keeps these, and it is off by default.

    Visit sources¶

    The places the visits of a research project can be taken from, besides entering them by hand, each set up on its own tab — the sources are WildINTEL Epicollect CSV, Custom CSV and Epicollect. Each can be used or not — but Custom CSV, which is always offered —: a check at the top of its tab (and a green dot on the tab); a source not used is not offered in Register the visits. The section is there so that other sources can be added in a future version.

    WildINTEL Epicollect CSV¶

    The visits are read from the CSV file downloaded from the new WildINTEL Epicollect project, the form of the field flow (Register the visits › WildINTEL Epicollect CSV). The columns are found by the label of their question: there is nothing to say about them.

    • The time of a visit — the form has no date or time to read: a visit happened when its entry was created (created_at, UTC), and it is told in the timezone of its location.
    • What is created — the Import & auto-creation rules card summarizes the options and opens with Customize. It has switches to create locations, cameras, SD cards and trappers the file names that are not kept, and three more (The photos were not counted, Use the coordinates of the location… and Close the revision before…). They are all marked at first for the WildINTEL CSV; the expanded card has a switch to mark or clear them all. With Create the locations on, it asks the timezone of the new locations — the form does not say it — (UTC by default), and, only when it is not UTC, whether their cameras follow summer time. In a custom CSV the entity-creation switches start cleared, because creating asks for more columns.

    Custom CSV¶

    Always offered in Register the visits, and it cannot be turned off. There is nothing to set up: the columns are matched when each file is read (see Custom CSV).

    Epicollect¶

    The connection to Epicollect5 and the mapping of its questions, to read the entries of a project directly: for the details of a deployment and, as a Custom CSV, for visits — its entries are downloaded as a CSV and read like any other.

    The Epicollect5 project the deployments' information will be imported from (see Dates and details): its slug, the name in its URL (five.epicollect.net/project/<slug>), and, only if the project is private, the client id and secret of its API client, which you create at https://developers.epicollect.net. Test connection reads the project with what is typed — saved or not — and says its name and how many inputs it has; a blank secret is the saved one. The Import deployment information from Epicollect5 switch turns the use of Epicollect5 on or off — it is off until you turn it on, and while it is off nothing is read from Epicollect5. Add them to the comments sends what an entry answers in the inputs that are not mapped to any field to the comments of the deployment, a line each (question: answer; image inputs are left out). Below, the Mapping relates each field of a deployment to an input of the project's form. Epicollect5 has no input for a date and a time together, so the day and the time of the start and of the end are mapped apart, along with the revision. What an entry gives fills the camera, the site and the notes of a deployment; it is no longer a source of its dates — those come from the visits, the timestamp log or the images.

    Validation¶

    Which of the folder checks the wizard shows. Each is an entry with a switch; turn off the ones you never want to see. They are all on by default.

    Postvalidation¶

    Which of the postvalidation checks the wizard shows, and what the ones that take a value mean:

    Setting Default
    Tolerance 1 hour Leeway around a deployment's start and end for the image dates.
    Sequence gap 60 s What a sequence is: a new one starts when the gap to the previous image is at least this.
    Compared with median What this revision is compared to: the median or mean of the earlier ones, the last one, or the range they span.
    Previous revisions needed 2 With fewer, the statistical checks are skipped.
    Number of images / sequences / length of sequences 50 % each How different a value can be and still count as similar.
    SD card / Photo count on The two checks of a deployment of a visit: that the card is the one the visit left and that the images are those it counted.

    Preprocessing¶

    What a new import does to the images — the wizard lists it before preparing, and a run can still switch each step off.

    • Steps — rename, resize, add metadata.
    • Resize width — 2400 px by default; wider images are shrunk to it, narrower ones left alone.
    • Authorship — Owner, Publisher and Coverage (where the images were taken; blank uses the deployment's location), written into each image. A blank owner or publisher is written as "Unknown".
    • License — picked from a list: CC0 (any use, no requirements), CC BY (any use with attribution) or CC BY-NC (with attribution, not for commercial purposes), the default. What is written into each image is the license's URL, shown beside each name.
    • Dates — Ignore summer time, and Convert the dates to UTC.

    Entities¶

    The things the visits and the deployments refer to, one tab each: Research projects, Trappers, Roles, Locations, Cameras and SD cards. A location whose time zone is not UTC has a red Not UTC label — in its line, in its form and in the panel at the right that opens when a site is pressed. Each can be added one at a time, taken from TRAPPER (research projects and locations) or loaded from a CSV with Import CSV — in the More button of each tab, with Export CSV and CSV template, the file with the columns that Import CSV reads and no rows, to fill in — (there are examples in examples/entities_example/wicp_02, explained in examples/CSV.md). Locations, cameras, SD cards and roles belong to a research project: pick it first. The trappers, the people, belong to none: they are the same whatever the project, and what each is in a project is its role. The page of each location, SD card and camera shows its QR code (it says wildintel:<camera|sdcard|location>:<research project>:<id>), with a button to download it as an SVG to print on a label. A location's time zone (UTC unless you say another) and whether its cameras ignore summer time are chosen when it is created and cannot be changed afterwards: the instant of every visit to it was worked out with them. The locations, cameras, SD cards and roles belong to a research project and are kept in its folder of the collections folder (<research project>/locations.json, cameras.json, sd_cards.json and roles.json, beside its visits.json), so they travel with its collections. The trappers, the people, are kept beside the folders of the research projects (trappers.json in the collections folder), not in the settings. Cameras, cards, roles and trappers kept in the settings file by an earlier version are moved to where they belong the first time they are needed. A camera or a card can be active or not; the visits only offer the ones in use.

    A trapper has a username — required, with no spaces, and no two trappers have the same, whatever its case: it is the account, an email, a special case —, a full name (how a visit says who went), an affiliation and an email, which are optional. The trappers kept before the username existed get one made from their name (Ana Pérez is ana.perez) when the settings are read. In Import CSV the columns are username, name, affiliation and email: a row with no username or no full name is left out, and said.

    The visits and the roles remember which location, camera, SD card or trapper they are of, not only what it is called. So correcting the label of an SD card, the id of a camera or the username of a trapper changes nothing else: the visits and the roles are still of the same one, and say the new name.

    Nothing is deleted for good. What is deleted — a research project, a location, a camera, an SD card, a role or a trapper — is kept, with the day it was deleted, and is only no longer listed; if it is added again it comes back with the day it was created. Everything also says when it was created and when it was last changed. What is no longer used is archived, which is a status of its own: an archived location, camera or SD card is still listed. A location can be deleted unless it has visits or comes from TRAPPER, and an SD card can be marked as stolen. Press Save to keep what you changed.

    Reports¶

    Every validation, postvalidation, preprocessing and repair leaves a report of what it checked and did, image by image. The step shows it right below its results — the same file you can download, so what you see is what is kept:

    • the checks, with how many images passed and how many failed each;
    • the images that failed, with the check and why — IMG_0087.JPG · Duplicate images · same content as IMG_0087 (copy).JPG — that can be narrowed to one check, and are shown 100 at a time;
    • Download CSV — a row per image and check, to open in a spreadsheet — and Download JSON, with everything: when it was made, the folder, the parameters it was run with and every entry.

    What each report holds:

    Report An entry for Says
    Validation each image and check — corrupted, shooting order, EXIF fields, duplicates —, and the folder for the structure and camera checks The ones that passed too, so the report says what was checked, not only what failed.
    Postvalidation the deployment for the naming and statistical checks, and each image for its date and camera Why a check failed — 241 images — like the previous revisions (median 238, ±50 %).
    Repair each image and check, and each metadata file What the repair wrote and what the images passed, as the new seal says — and the preprocessing checks: names, size, metadata.
    Preprocessing each image What was done — IMG_0001.JPG → R0003-DONA_01__20240904_1.JPEG; date 2024-09-04T11:10:00+00:00 (exif); resized — and the ones that were skipped, with the reason.

    Settings › Reports lists all of them, newest first, with View, CSV, JSON and Delete (which asks again). They are kept in the reports folder of the data folder until you delete them. A check you run twice makes two reports.

    Multiple configs¶

    The application lets you define several different configurations: + adds one with the default values, and choosing one makes it the active one — handy to switch between two TRAPPER servers (a test one and the real one) or two sets of authorship. Each can be downloaded, and its folder opened.

    3. The task menu¶

    Once it is configured, the menu is where you choose what you want to do. The three actions — register the visits, import the images and upload the images — are in three columns, numbered 1 to 3 in the order of the work; under them, the dashboards and statistics and the utils are a bar each, full width, with its button (Open dashboards, Open utilities) at the right:

    Task What it's for
    📋 Register the visits Record the visits to the camera traps: who went, when, to which site and what was done — one by one, or from a file.
    📷 Import the images Import the images collected in a visit: pick the collected visits whose images you have and create their deployments — one, several at once, or one after another.
    ☁️ Upload the images Upload deployments to platforms: send a deployment already kept locally to TRAPPER.
    📊 Dashboards and statistics A bar that opens, under it, the list with the visit dashboard, the deployments dashboard, the uploads dashboard — each revision with how many of its deployments are on TRAPPER — and the statistics.
    🧰 Utils Check and fix dates and times compares the dates of a folder's images with the period of the visit, when the camera clock went wrong, and shifts or removes the ones that cannot be trusted (every fix is written down). Maintenance of the local collections: Sync local collections brings the collections folder up to date with what TRAPPER already has, and Repair local deployments checks which deployments are still valid and writes the metadata files of the others again from their folders.

    The Quick guide button, at the right of the title, opens a panel with the work from end to end: the research project and then the three steps, and where to follow the progress and to fix dates and files. The numbers of the cards are the typical workflow: 1 Register the visits, then 2 Import the images — which takes the location, the camera and the dates from the visits — and then 3 Upload the images. Sync is for when TRAPPER already holds deployments that this computer's collections folder doesn't know about (Utils › Sync).

    The title in the top bar takes you back to the welcome screen at any time; ? Help opens this documentation, and the sun/moon button switches between dark and light.

    If the app was closed in the middle of an import, the first thing you see is the list of unfinished runs — see Unfinished runs.

    4. Unfinished runs¶

    An import saves its progress as you go. If you close the app, or it fails, the next time you start it the first screen lists the unfinished runs — the folder, the research project and when it was started — each with Resume and Discard. Resuming takes you back to the step after the folder was chosen. Passwords are never saved with a run.

    5. Register the visits¶

    The Register the visits task opens visit registration. Open Visit dashboard from Dashboards and statistics.

    Visit dashboard¶

    The dashboard is of the default research project. Choose another project using the Research project selector in the header. The dashboard has the following buttons:

    • Export visits (CSV) — downloads the visits kept as a CSV that Register the visits › Custom CSV reads back as they are (it is there when the project has visits).
    • Register the visits — goes to Register the visits without going back to the menu.
    • Select visits and create their deployments — each row has a box (and one in the header selects the page). Once visits are ticked a bar appears over the table: N selected, Select all N matching, Clear and Create deployments →. The button is only active when the card of every visit ticked was collected (Collected), they have no deployment yet and they are of one revision; the bar says why when it is not. With one visit it goes to Import deployment; with several, to Import deployments, with those visits ticked.
    • Create the next revision — plans the next trip: the visit book gets the next revision (R0003 after R0002) with a planned visit to each location that can be visited — the ones that are not archived and not only planned in the settings, that is, ready or active —, and opens on it. A revision is one visit to every location, so the one before has to be finished for visits to be made in the new one: if it is not, a message says which locations are still to be visited in it and that no visit can be made in the new revision until it is finished — make those visits, or press Mark them as not visited (it asks again before it does it: the visit book of that revision is then consolidated and cannot be modified). That message is not only for the moment the revision is created: whenever the book has a planned revision with no visit and the revision before it is not finished, it is shown, with its button, so the revision before can be finished from there.     Register the visits¶

    Press Register the visits.

    A visit is one trip to a camera trap: when it was, which site, who went and what was done. The visits of a research project are kept in its visits.json, and the deployments are worked out from them: a deployment goes from the visit that left a camera to the one that collected its card. Choose the research project and how the visits come in:

    Source What it does
    By hand You fill in each visit yourself, following the field flow: the site, when, who went and what was done.
    Custom CSV A CSV of any shape: the page shows its columns and you say which one gives each field of a visit. When Epicollect is turned on in the settings, the CSV can also be the entries of an Epicollect5 project (Epicollect5 project › Download the entries), read the same way.
    WildINTEL Epicollect CSV Reads the visits of a field trip from the CSV downloaded from the new WildINTEL Epicollect project (the form of the field flow): the columns are found by the label of their question.

    The rules of a visit¶

    A visit follows the same rules by hand and from a file: the one that breaks them is refused — by hand, with the reason; from a file, with its row and a label of its own for each rule. The rules compare the visit with the visits before it by date — not only with the revision before — and with the other visits of its revision:

    Label in the results What it says
    Site is not a location The site is not a location of the research project (see Sites that are not locations, below).
    Visit already there at that time The site already has a visit on that day and at that time.
    Site visited twice in a revision A revision is one visit to each site, whatever the day.
    Visit not after the last one of the site / Revision out of order A visit is after the last one to its site, and a revision is after the revisions before it and before the ones after it.
    Revision started before the one before is finished A revision starts when the one before it has a visit in every location that is not archived.
    Revision closed Every location has its visit in that revision: nothing new is added to it.
    First visit is not an Installation The first visit to a site puts the camera up.
    Something its actions ask is missing An Installation asks for the camera and the card it leaves; a Revision, the camera and the images it collected (not when the card was full); a Desinstallation, the camera and the images; a Stolen camera, the camera.
    Not the camera at the site, Camera already installed here, Camera installed at another site A Revision, a Desinstallation or a Stolen camera is of the camera that is at the site (to change it, add an Installation to the visit); a camera is not put up where it already is, nor while it is at another site.
    SD card archived, SD card left is the one collected, SD card in another camera, SD card collected in this revision The card left is not archived, is not the one the visit collects, is not in the camera of another site, and was not collected in the same revision.
    Site archived, Archive with an Installation, Camera still there when the site is archived An archived site has no visits after the day it was archived; a visit that archives it puts no camera up and takes the one that is out away (or finds it stolen).
    Camera not in the research project, SD card not in the research project, Trapper not in the settings The camera, the SD card and who went have to exist — by hand and in a file — unless the import is asked to create the camera or the card.

    What the form only questions — a Revision with no images, a camera or a card at two sites in a revision — is still kept, with a warning.

    What an unknown revision hides is not checked. A revision before the first visit of a site is unknown: nothing is known of it — no day, no camera, no card. So the first visit to a site in a revision after R0001 may be any, and what a visit left at a site (which camera is there, which card is in it) is not trusted for a later visit when an unknown revision of that site lies between them: nobody knows what was done in it. An unknown revision counts as a visit to finish its revision, and a real visit that comes later takes its place.

    A visit already kept is the one of the same revision and site, whatever the day: a row like that is left as it is and counted as already kept. Only a row with no revision — it gets the next of its site — is told by the site, the day and the time.

    • Sites that are not locations. A site of the file that is not a location of the research project may be a site that is really new or one misnamed in the field. Its visits are held, and the site is shown with what tells the two apart: how far its first visit was from the nearest location, and the locations whose id is one character apart from its own (it may be a misprint). If it is new, create it — by turning on Create the locations that do not exist in the first step (the file then gives the coordinates of the location, location_latitude and location_longitude, besides its timezone and daylight_saving) or in Settings › Locations — and read the file again; if it is a misprint, correct the id in the file and read it again.

    By hand¶

    A visit is a form with these parts:

    1. Actions — one or several of Installation (a camera is put up and a card left), Revision (the card is collected and another left), Desinstallation (the camera is taken away with its card), Stolen, Archive (the site is given up) and Site start (the site begins here: said once, with its first visit, as Archive says it ends). In the form that asks questions, the first visit ever to a site in a revision after the first asks whether it is where the site starts — off by default, as the site may have been there before with its earlier visits not in the app; in the first revision it is where it starts, and nothing is asked. A site with a Site start is not waited for in the revisions before it: they do not need a visit to it, nor an unknown one. A site with none keeps what it had: what came before it is unknown. The first visit of an existing site can be edited to add it. It also gives the site its state: planned (only in Settings: it cannot be used, a start included) → pending (in the app, not started: what a new location is) → ready (it started and has no camera) → active (it has a camera) → archived. A pending site is not waited for in the revisions until a visit to it is known, and the first camera put up at it says Site start by itself, so the form does not ask; a ready or active site, which started before or whose start is not known, is asked in the form (off by default). The rest of the form depends on what is chosen: what the actions do not ask is left out. When the camera was already visited, the Camera, Site and Grouping sections come filled in from the last visit (not its notes).
    2. Camera — the camera (picked from the active ones of the project, or added from here) and how it is placed and set: height or depth, tilt, heading, delay, detection distance, its status, whether the batteries and the clock were right. It comes before the SD card.
    3. SD card — the card left in the camera, how many images the card collected, and whether it was full. It says which card was in the camera according to the visit before.
    4. Site and Grouping and notes, as in the details of a deployment.

    Each field is marked required or optional according to the actions.

    The camera and the SD card are picked from those of the research project, and who went from the trappers of the settings; the form is refused if they are not. The rules above are checked by the server, whatever page sends the visit, and the form says why a camera or a card cannot be used as soon as it is chosen. A visit that is wrong can be edited from the dashboard, with the same rules checked — also on the visits after it that the change touches.

    Custom CSV¶

    Any spreadsheet with a row per visit. Press Register the visits › Custom CSV; the research project is the default one. The steps:

    1. Choose the spreadsheet file. When Epicollect is turned on in the settings, first say where the CSV is: A file on this computer or Epicollect5 project — with the latter, Download the entries reads them from the project of the settings and goes on as a file does. Drop the CSV in the file area or browse for it. Choosing the file does not move on: the step stays open with Import & auto-creation rules, where Customize opens the switches for entities the file names that are not in the project; each asks for more fields in the matching, where a default can also be given (a location is created with its own coordinates, location_latitude and location_longitude, which are not those of the visit). Done closes the options; Continue moves on.
    2. Match the columns. For each field of a visit, the column of the file that gives it. The fields are in groups, as in the form of a visit by hand — Who, Where, When, The visit, SD card, Camera, Site, and Grouping and notes —, each with an example from the file. Each group is a card with a chevron at the left that folds it away, and says how many of its fields are matched (3 of 5 matched). What has the name of a field (location_id, session, date, time, actions, trappers, camera_id, sd, num_photos…) is matched by itself; pick the rest, or give a default for a field the file has no column for. The site and the actions are required — every row gives them, by a column or a default. The coordinates of the visit (latitude and longitude: where the trapper was when the visit was noted) are required of a visit, but the file need not have them: a row gives them by a column or a default and, when it gives none, takes those of its location (a note says how many rows did) — the switch Use the coordinates of the location when a row has none, on by default, in the options of the second step; with it off, a row with none is refused —; one of the two alone is refused; the time is a date and a time, or — when the file has it — the instant of an entry (created_at), as the visit sources setting says. Dates may be written day first. A visit with no revision gets the next one of its site. Press Read the visits.
    3. Check the visits of the file. The check starts when you press Continue in the step of the file, not before. While it runs nothing is shown but that the file is being checked (a long history can take some minutes): a bar that moves — it does not say how far the check is — and the number of the step turns like a clock. Then what the file says, before it is kept: N visits to add · N already kept · N rows with a problem, the new sites, what is worth knowing and what is odd. Then the rows of the file, laid out like a dashboard:
    4. Revision selection — a card for All revisions and one for each revision the file has (the five most recent as cards, the older ones in the Older revisions list, for a file with many). Picking one narrows what is below to its rows.
    5. Status metrics & filters — the Progress card and a card for Rows read, Ready (new visits), Skipped / Existing (already kept, or ignored) and With problems. Pressing one shows only those rows; pressing it again shows them all.
    6. The table — the search (by row, site, visit, action…), Group by — Row or Error — and Reset, with a line of the active filters. Grouped by row, each row of the file has its Row, Visit, Site ID, Actions, When and Status (Add, Add · to check, Skipped / Existing, Skipped / Ignored or Error); the chevron at the left is only in the rows with something wrong, and opens the errors under the row — a row that is fine has none —, and the row is marked with a blue band while they are open; the eye button opens a panel at the right with what the row says, field by field, and what is wrong with it when something is (Escape or Close shuts it). Grouped by error, each kind of error is a row with how many rows have it, and its chevron opens those rows.

    When the rows of a revision are refused because the revision before is not finished — R0043 cannot start: R0042 is not finished, 3 location(s) still to be visited in it: … —, a notice above the metrics says which revision and which locations, and has the button Mark them as not visited and read again: those locations get a visit Not revised, the revision before is closed — it cannot be changed afterwards —, and the file is read again. The other way out is to correct the file and read it again. The switch of the second step, Close the revision before when it has locations still planned, does the same beforehand.

    An SD card whose id has spaces or signs (84 (10), 38_B) is told among what is odd — it is kept as written, not refused; the ids of the cards are never upper-cased. The case counts for an SD card, a camera and the full name of a trapper (not its username, which is read whatever its case): 7b and 7B are two SD cards (they were two sites), and a visit that says 7b is of the card 7b, not of 7B. The sites and the research projects are still read whatever their case: they are names of folders, and TRAPPER keeps its ids in lower case.

    Worth knowing is collapsed: open it to read it. Continue to the review goes on to step 4. 4. Review and confirm. It says what is going to be saved — the visits, the revisions and sites, and the locations, cameras, SD cards and trappers that are created —, warns that the visits cannot be changed once they are created, and has the button Add N visits. Once they are added the same step turns green (Visits saved), has What was saved collapsed — open it for the summary —, the deployments that can now be created and what to do next.

    The trappers must be registered first — in Settings › Trappers —, or the rows that say them are refused (Luis Gómez is not one of the trappers), and with them every revision after. Turn on Create the trappers that do not exist, in the options of the second step, to make them from the file: each person a row says went — who went and set up by — who is not a trapper yet is made as the row calls them, the username is worked out from the name (Ana Pérez is ana.perez, ana.perez2 if that one is taken) and a note says it; complete them in Settings › Trappers. Only the people of the rows that are kept are made.

    An old datasheet with no image count. A Revision or a Desinstallation needs the images counted on the card, and a file that has none is refused. Turn on The photos were not counted, in the options of the second step, to accept those rows as they are: the count stays empty — no number is invented — and a note says how many visits have none. The images of their deployments are then not checked against a count they do not have (as for a card that was full); a made-up count would only say that images are missing.

    Press Add N visits to keep them.

    When the visits are kept, the end says how many were added and, if they collected other visits — a visit collects the card left by the visit that started the deployment —, how many: pick their revision and import their images is a link to Import deployment on the research project. A report of the import is written with the other reports.

    The rows are read as their fields take them: a date that is not a date, actions that are not Site start, Installation, Revision, Desinstallation, Stolen or Archive (New site as the status of the camera says Site start, even when the location already exists), a card code that is not OK, Card full, No batteries or Card full and no batteries, or image counts that are not a whole number, are rows with a problem, and none of them is kept. The visits are then checked with the rules of a visit, in the order of their instants, each against the ones kept and the ones of the file before it. The visits of a file that fill unknown revisions of the visits kept are checked together, with the ones after them that they touch.

    There are example files of every case — all correct, three revisions, a revision that starts before the one before is finished, unknown sites, rows that cannot be read, a card that is left where it cannot be, a theft and a site given up, columns to match by hand — in examples/visits_example, in folders by the option they are for — custom_csv/wicp_02 and wildintel_csv/wicp_02 —, made for the entities of the research project WICP_02.

    The deployments the visits say, and the logs of the collections. The name of a deployment isolates it in the figures. Under its state, a button says how its images a day changed against the revision before of its location — More activity from +12%, Unusual peak above +45%, Less activity from −12%, Sharp drop below −35%, Stable between, and First revision when there is none before — and opens the comparison: the six metrics side by side (length, images, images per day, sequences, images per sequence and the longest sequence, with the difference and the change in %), how the location evolved revision by revision, and a profile of its bursts against the reference. It can be compared with the previous revision, with the mean of all the previous ones, with a revision of its location that you pick — in the list, or by pressing its bar in the evolution —, with the rest of its revision or with the whole project; the reading also says why a deployment is To review (what is outside the tolerance of Postvalidation), and the arrows go to the deployment before and after it. Press its arrow, or its images per day, to see a histogram with a column for each calendar day — the days with none empty — or its sequences to see those that began each day and how many there are of each size.

    The command line has the same: statistics collection and statistics compare (see the command reference).

    Import a deployment¶

    Press 📷 Import the images, then Import deployment. This option is meant to import the set of images that come from a single camera: one folder, one deployment. For a folder with the images of several cameras, one subfolder each, use Import deployments.

    It is a wizard of five stages — the bar at the top shows where you are, and a stage can have steps of its own, which open one after the other. Each stage is done (a tick and a summary, with a pencil to go back and change it), open or locked until the ones before it are done. Back and Continue move between them.

    Stage What it asks
    1. Origin The research project and the visit (or the location) the images are of.
    2. Images Which folder, which SD card, which checks, and how the images did.
    3. Dates and details The revision, the period, and what you know of the camera and the site.
    4. Check details The deployment's names and dates, the images against them, and against the visit.
    5. Prepare and save The preprocessing, and saving the deployment in the collection.

    The bar of chips above each stage fills in as you go: the research project, the visit with its range of dates, the number of images and the card, and, at the end, the id the deployment will have, its location and its dates.

    Stage 1 — Origin¶

    Where the images were taken, which tells the app what the deployment is of. It is of the default research project; choose another using the research project selector in the header. If there is no default one, the step asks for the research project: pick one of those in the collections folder, or add a new one by hand or from TRAPPER (the app uses the account saved in the settings).

    When the project has collected visits the step is When was it collected?:

    • Revision — a revision is one visit to every site. A card for All revisions and one for each revision that has visits that can still be given a deployment, with how many. Pick one — or all — to narrow the list below.
    • Collected visit — the visits to the project that left a camera and whose card has been collected, and that have no deployment yet (a visit that already has one is not offered). Picking one gives the deployment its location, its revision and, later, the camera, the site and the period: the deployment is of that visit.

    If you start from a visit — from Register the visits, or with Create the deployment of the Deployments dashboard — the project and the visit are already chosen.

    When the project has no collected visit there is nothing to import yet: a deployment is always linked to a visit — the one that left the camera and the one that collected its card — so the step says there is no collected visit without a deployment in the project and offers Register the visits, by hand or from a file with their history. Once they are registered the visits are offered here. The app also refuses, before touching any image, a deployment that is not of a visit of its research project.

    Stage 2 — Images¶

    In this stage you tell the app which images you are importing and find out, before anything else is done, whether they are in good shape. You choose the folder with the images of the camera and the app counts what is in it; then you choose which checks to run over the images alone — corrupted files, shooting order, subfolders, a single camera, the image data they need and duplicates — and how strict each one is. The result tells you how many images are valid and which ones have problems, so you can fix them before going on. Nothing is copied or changed yet: the source folder is only read.

    The stage has three steps (the first one also asks the SD card):

    1. Select the folder. First say whether the images are on an SD card:

    • Yes, they are on the SD card — say where the card is (Browse…, or type it) and press Copy the card. The card is only read: its content is copied to a temporary folder of this computer, with the progress of the copy, and the card is ejected so that it can be taken out. The process goes on with the copy as with any folder, and the copy is removed when the import is over.
    • No, they are in a folder — press Browse… and choose the folder with the deployment's images (or type its path), then Scan.

    The scan only counts: how many files there are and how many of them are images (by their extension) — 241 images found — with a warning if the folder is empty or has no images. It doesn't open them, which is why it is instant however many there are: reading the images is what the next steps are for. A folder you choose is read where it is, and nothing in it is changed.

    Once the folder is scanned, the app asks the SD card the images come from, among the cards of the research project (Select an SD card…; optional). If the deployment is of a visit, the card is checked against the one the visit left — see Check details.

    2. Choose the checks. Checks over the images alone, before anything is known about the deployment:

    Check Looks for
    Corrupted images Files that aren't readable images.
    Shooting order vs. filename sequence Images whose order by name differs from their order by time.
    Folder structure Subfolders inside the deployment's folder.
    Same camera More than one camera model or id among the images.
    Required photo data Images missing the capture date, camera model or id.
    Duplicate images Files with the same content.

    For each check you choose how strict it is: Skip doesn't run it, Warn shows the problems but lets you continue, Must pass stops you from going on while it fails. The ones that are turned off in the settings are not shown. Press Run checks: the Continue of the page is there once the results are open, and it is not active while the checks run.

    In the checks of the deployment, Image dates fit the deployment and The SD card is the one the visit left are Must pass by default: images out of the range of dates of the deployment, or that come from another card than the one the visit left, are an error, and the step does not go on until they fit — or you set the check to Warn to accept them.

    3. Results. When it was last run, with the download of its report, and then two blocks like those of the dashboards, each of which folds away:

    • Images status & filters — Images reviewed (all of them, with a bar split between the ones that are fine and the ones with errors), Without errors and With errors.
    • Checks status & filters — Checks finished, Checks passed and Checks failed.

    Pressing a card filters the table of results below, and each block filters on its own. A message says whether you can continue, and the table has a search, Group by — Test or Image —, Results (All results, Only issues / failures or Only passed), Reset and a line of the active filters:

    • By test, one row per check with its status (✔ passed, ⚠ failed, ✘ failed and Must pass), how strict it is and how many images failed it. The chevron of a check that failed opens which images failed it: as pictures, each with what is wrong with it (No date, Duplicate, Out of order…) and when it was taken, or as a list (the two buttons of the view). You can search by file name, filter by the kind of error and go through the pages. A check of the whole folder (the structure, or the camera) has no pictures: it says what it found.
    • By image, one row per image with how many checks it failed (1 failure of 4); the chevron lists every check, passed or not, and the two buttons of the toolbar show the images as a list or as pictures.

    View details of an image opens a panel at the right with the image bigger, when it was taken and the result of each check on it. Run again repeats the checks.

    Reading the camera's model and id uses ExifTool, because the serial number of a camera trap lives in the manufacturer's own metadata. Without it the app falls back to the standard EXIF tags, which are less complete — it says which it used.

    Stage 3 — Dates and details¶

    Here you tell the app when the images were taken and what you know of the camera and the site. With this the deployment gets its id (R0003-DONA_01) and its details. Only the dates are required: the rest can be completed later. The stage has two steps.

    1. Dates of the deployment — called When was it collected? when the deployment is of no visit.

    First, the revision. If the deployment is of a visit it is the revision of the visit, and is not asked; otherwise it starts as the next one expected for the location — one more than the highest kept — and says so; change it if needed, and the deployment id is built (R0003-DONA_01). If an earlier revision of this deployment is kept, a notice offers to copy from it its camera, site and notes — the dates are never copied. If the deployment already exists in the collections folder you are told, and the import would be refused as it would mix two sets of images: choose another revision or location, or move that folder away.

    Then the period: when the camera started and stopped recording, as the clock of the location's timezone. The dates always come from the visits: from the visit where the card was left to the one where it was collected. The card Recording period shows them locked — Locked · Field work (R0002 → R0003) —, the start and the end each with its visit, the duration and the timezone. Edit dates unlocks them: the form to type the start and the end appears, marked Unlocked · Custom override, with Cancel, Apply changes and Restore from Visits of the field work, which gives the dates of the visits back. The visits are never changed.

    If the deployment's collection has a <COLLECTION>_FileTimestampLog.csv (the file wildintel-tools asks for), going on from More details adds the deployment's row to that file. A log that is already there is used for the dates in an Import deployments.

    2. More details.

    After the dates, the app shows deployment details in the Camtrap DP format — the same fields as TRAPPER's own deployment form. Most fields are optional and can be completed later in TRAPPER. The app pre-fills available details from the field visit where the SD card was left (and from the previous deployment, when available); you can review or edit them. Each section is a card that says how many of its fields are filled in; open it, with the chevron at its left, to fill it in.

    Section Fields
    Camera Camera id and model (read from the images when they all share them), delay between triggers, height or depth (not both), tilt, heading, detection distance.
    Site Feature type (road, trail, burrow, water source…), habitat, set up by, bait used, timestamp issues.
    Grouping and notes Deployment groups, tags, comments.

    Pre-filled details. The details are what the previous deployment of the location says, overwritten with what its visit says — only the values that are not empty; a visit that was not made, or that is unknown, says nothing. The card Pre-filled details says it: Locked · Previous deployment (R0001-DONA_06) & Visit R0002, a sentence with where the data comes from — Data comes from previous deployment R0001-DONA_06 and field work visit R0002 (16 Nov 2020, 14:24 UTC). Original records are never modified. — and a chip for each source with how many fields it gave. Under it the sections — Camera, Site and Grouping and notes — are locked: each has its padlock, its line says which source gave its values (From Visit R0002 & R0001-DONA_06) and how many fields are filled. Edit details unlocks them: the fields open for editing without losing the values, and Restore the pre-filled details gives back what the sources say (what you changed by hand is lost). When Epicollect5 is turned on and has an entry, a notice under the revision also offers Import from Epicollect5, which fills the camera, the site and the notes from it (and leaves the form to be edited by hand); the location's own data are never taken from the entry.

    The form is validated as you type, in the browser and again in the server: dates in order, latitude and longitude in range, tilt between −90 and 90, heading between 0 and 360.

    Stage 4 — Check details¶

    Now that you know when, how and where the images were taken, new checks are run: the deployment's names and dates, and the images against it:

    Check Looks for
    Deployment id format R0033-DONA_01.
    Deployment id starts with its collection R0033-… belongs to R0033.
    Collection name R0033.
    The id's location is the one chosen The location in the id is the one from stage 1.
    Image dates fit the deployment The first image at the start, the last at the end, within the tolerance.
    Camera consistency The camera in the images is the one in the details.
    Number of images Like the previous revisions of the location.
    Number of sequences Like the previous revisions of the location.
    Length of the sequences Like the previous revisions of the location.
    The SD card is the one the visit left Only for a deployment of a visit: the card said in stage 2 is the one the visit left in the camera. A card nobody said passes, with a note.
    The photos are those the visit counted Only for a deployment of a visit: the number of images is the number of images the visit that collected the card counted. A visit that counted none passes, with a note.

    The three on the number of images, the number of sequences and their length are statistical: a location is visited again and again, so what earlier revisions looked like says what this one should — about as many images, about as many sequences, as long. A camera that fired non-stop, or died early, stands out, and is worth a look before it is uploaded. They need at least the previous revisions needed of the settings, or they are skipped; what a sequence is, what "similar" means and what it is compared to are the Postvalidation settings.

    For a single deployment the results are laid out as those of the images' checks — the Images and Checks blocks and the table of results, by test or by image. If some images were taken outside the deployment's dates, a notice offers Fix the dates and times, which goes to Check and fix dates and times; fix them there and run the checks again.

    When the checks are run on a collection, the results show the same as those of its deployments: the figures, a message that says whether you can continue, and the deployments — or, by check, the table — with the checks each one failed, View the images and Download report.

    It has the same two steps as the images' checks: choose how strict each one is (skip, warn, must pass), press Run checks, and read the results — when it was run, the figures, the table, and, opened from a check, the images that failed it (Out of range, Other camera) as thumbnails. The report downloads.

    Stage 5 — Prepare and save¶

    1. Processing steps. Choose what to do to the images; the table says what each step does. Press Start preparing.

    1. Copy into the collection — always. Anything that isn't an image is copied as it is.
    2. Read the capture dates — always. From each image's EXIF, as the camera's local time in the location's timezone — ignoring summer time and converting to UTC, as the settings say. An image with no EXIF date uses its file's date.
    3. Rename the images — <DEPLOYMENT>__<YYYYMMDD>_<n>.<EXT> in upper case, .jpg becoming .jpeg, e.g. R0003-DONA_01__20240904_1.JPEG; n is the image's place in file-name order.
    4. Resize the images — to the width of the settings, keeping proportions, EXIF and colour profile. Unlike wildintel-tools, the resized image is the one that is kept.
    5. Add metadata — authorship, rights and license, written into each image as XMP with ExifTool: Creator, Owner, Publisher, Rights, License, Coverage and the hash of the original and of the image kept, so each can be traced back. It is switched off, with the reason given, if ExifTool isn't available. Check the owner and publisher in the settings first: if they're blank, the step says so.

    Each optional step can be switched off for this run (its checkbox). Its values come from the Preprocessing settings. The images go into the deployment's folder in the collections folder; the originals are never touched. Nothing is final yet: you can go back, change something and Prepare again — the folder is simply redone.

    2. Processing results. The images processed and skipped, a status for each step and, opened from it, the skipped images as thumbnails. The report says what was done to each image. Continue to save goes on.

    3. Review and save.

    The images are ready, so this step consolidates the deployment: it says what is going to be saved, in a card (the deployment, where it was taken, its period, the images and where it is kept), a box with a lock says that saving seals the deployment and asks Do you want to save the deployment … in …?, and, at the foot, Back at the left and Save to my collection at the right — as when the visits are saved — writes its deployment.json, moves the deployment to its place in the collection and seals it. From then on it can't be modified — the app notices if an image or its details change — and it can be uploaded.

    Until you save, the images are prepared in a hidden .staging folder inside the collection (<collection>/.staging/<deployment>): the collection has nothing of the deployment, and what an interrupted preparation leaves there is cleared when the deployment is prepared again. Saving moves the folder with a single rename, so it is instant however many images there are. On Windows, if another program has one of its files open for a moment (the antivirus, a viewer), the move is tried again for a few seconds before it gives up.

    Once it is saved, the steps before are locked (they show a padlock) and the same step turns into what was saved and what to do next. It has:

    • a Deployment saved notice with the id of the deployment;
    • What was saved, collapsed — open it to see it —: how many images and what was done to them, that its metadata is written and sealed, and where it is kept, with Open folder and Copy path;
    • Upload: Not uploaded yet, with Upload to Trapper — straight to the upload page with the research project and the collection already chosen — and Add another deployment, which starts again at stage 1;
    • and, below, links back to the Import the images task and the Main menu.
    • The back links return to the task menu or the main menu, as when visits are registered.

    What gets written next to the images¶

    File Content
    deployment.json The details of stage 3.
    images.json Per image: its name (and the original, if renamed), when it was taken — the camera's wall clock and the instant —, the camera, size and pixels, and hashes. It lets later checks, and the statistics of the next revisions, work without opening the images again.
    preprocessing.json What was done to each image, with its hashes: source_hash of the original, hash of the image kept, final_hash of the file with its metadata.
    seal.json Which validation and postvalidation checks the deployment and each image passed, and the hash of everything.

    The seal protects against changes by mistake: if an image or deployment.json is changed after the import, the seal no longer matches, and the app can tell. It is not a signature — whoever edits the files on purpose could seal them again.

    7. Import deployments¶

    Press 📷 Import the images. It works from the visits of the default research project: choose a revision — a square for each one (All revisions, R0003…) with how many collected visits without a deployment it has — and the visits whose images you have. The latest revision is picked, with all its visits ticked; picking another ticks its visits, and you take off the ones you do not have. The visits are in the same table as the dashboards, filtered by Collected, with a box in each row. With no visit whose card was collected it says so and offers Register the visits: a deployment is always of a visit.

    • One visit: it works as Import deployment: the folder is the deployment's, with its images in it (no subfolders), and it is linked to the one visit. Only its SD card is asked beside it.
    • Several visits: a card How do you want to import them? asks for All at once or One after another.
    • One after another (Start with the first) runs Import deployment for each visit, the first, then the second…: Deployment 3 of 38 is at the top, with Skip this one and Stop here, and when one is saved the button is Next: R0001-DONA_0007 (4 of 38) — Finish on the last. The folder of the images of the first is told to the next: Beside the one before proposes <the folder above>/<the deployment>. Stopping leaves the visits that were not imported as they were: they are collected visits without a deployment, and they are offered again.
    • All at once: the folder is a collection: a folder with one subfolder per visit, as follows. A collection is a folder with one subfolder per deployment — the usual way a field trip's images come home. The revision, the checks and the preprocessing are the same for all; the location, dates and camera are asked for each deployment.

    The stages are those of Import a deployment, with the differences below.

    1. Origin — select the visits whose cards have been collected (see Register the visits): those of one revision. The list has a search (by site, card, date…). With no collected visits without deployments, register visits before importing.
    2. Images — Revision folder: choose the folder and Scan; its subfolders are listed, each with its images and warnings, and you tick the ones to import. With visits, each folder is linked to a visit — a folder named after a site takes the visit of that site by itself; change it if it is not right — and says its SD card (optional). A header above the list says how many of the ticked folders have a visit, with a progress bar, the tabs All, Missing and Ready and a filter by name; a folder with no visit has to be linked or unticked before going on, and a visit is of one folder only. Then Choose the checks and Results: the checks run over every chosen deployment, by folder or by check (with Only folders with problems). Leave them out drops the folders that failed from the import; Continue with N folders goes on.
    3. Dates and details — the locations are the visits': nothing is asked of where they were taken and the stage starts at When was it collected?. When was it collected?: first the revision, common to the import, which names all the deployments (R0003-DONA_01, R0003-DONA_02…); it is the revision of the visits, or is taken from the log's ids. Then the list of deployments, each with its period and where it comes from (From the visits, From R0003_FileTimestampLog.csv, From the images, Entered by hand), how many are complete ("12 of 40 deployments complete"), a filter by name and Only the incomplete ones. More details: the camera and the site of each; for a deployment of a visit, the same source card as in a single deployment — the field sheet, the previous deployment or by hand — for each one.
    4. Check details — the deployments' checks, by folder or by check; for deployments of visits they include the two checks against the visit (the card and the number of images).
    5. Prepare and save — one list of preprocessing steps for all, then each deployment in turn, with its own result. If some fail, Import the N left resumes with the ones that are still pending. Saving seals each of them, and links each visit to the deployment it gave.

    The chips above each stage fill in as you go: the research project, the visits with their range of dates, the images and the cards, and, at the end, the revision, the deployments and the dates they cover.

    When it ends, Upload the images goes to the upload page with the collection chosen.

    Where the dates of each deployment come from¶

    Each deployment has its own period, the one its visits say, in the same card Recording period: locked, with Edit dates to unlock it, Cancel, Apply changes and Restore from Visits of the field work, as in a single deployment.

    When the revision folder contains a timestamp log, the scan shows which folders match it, the dates it contains and any unmatched rows. For deployments linked to visits, the recording period uses the visit dates; open the deployment and use Edit dates if those dates need to be adjusted.

    8. Upload the images¶

    Press ☁️ Upload the images. (The other option, Uploads dashboard, shows the created deployments of the default research project by revision: a square for each revision, to pick one, and a ring that counts the uploads done over the most there can be: the deployments of the revision times the uploaders picked. To its right, where they were uploaded: All and a card for each uploader (Trapper for now, more to come), which show how many went to it and pick it. The table has, for each deployment, Where, When (the visit that started it, a link that opens the visit dashboard on it, and the period) and whether it was uploaded: a label for every uploader it went to, with the day, or Not uploaded. The deployment's name is a link to its details in the Deployments dashboard; View opens the list of where it was uploaded, when, and a link to reach the upload; and a deployment not uploaded to the uploaders picked has an Upload button, which opens the upload page on its revision. There is a search and a Show filter (all, uploaded, not uploaded).) It sends deployments kept in the collections folder. For each one it does what wildintel-tools did in three commands:

    1. creates the location in TRAPPER, from the deployment's coordinates, if the research project doesn't have it, and the deployment, from its details;
    2. packs the images in zips and the yaml that describes them — what was recorded when —, splitting in several parts when a zip would be larger than the limit;
    3. uploads each zip and its yaml, and tells TRAPPER to process them into a collection.

    The deployment must have been imported with the wizard — the yaml needs the dates its preprocessing.json records. One that wasn't says "Not preprocessed — import it again through the wizard before uploading it", and can't be ticked.

    A note at the top says which TRAPPER account is used: the one saved in the settings (Change in Settings takes you there; Test connection is in Settings › Uploader › Trapper). The page is a wizard of its own.

    Step 1 — Choose what to upload¶

    1. Research project — the default project is used; change it with the selector in the header.
    2. Revision — choose the revision to upload. Its deployments appear in a table with their dates, image counts and whether TRAPPER already has them. The ones left to send start ticked; use the checkboxes or the selection menu to change the choice. The page reports whether the project and revision are found in TRAPPER.
    3. Classification project — the collection is created in one of TRAPPER's classification projects for the research project: pick it (or, if there is only one, it is used). Without a TRAPPER account, type its pk.

    Step 2 — Choose what to do¶

    Mode What it does
    Upload to Trapper The real thing.
    Rehearse first (dry run) Looks at TRAPPER and says what would be created and how the images would be packed. Nothing is created, sent or written.
    Only prepare the files Writes the zips, the yamls and the collection's _deployments.csv and leaves them, to send some other way. Needs no account if the research project was filled in from TRAPPER.

    With Upload to Trapper, tick Delete the package files once they are uploaded to take the zips, the yamls and the deployment's row of the _deployments.csv away when TRAPPER has them. Unticked (the default) they stay in the packages folder, as when only preparing them, and the result says where. The option is also offered when you go on to upload files you have just prepared.

    The size of the zips is a setting: Settings › Uploader › Trapper. The page says what you will get before you go on.

    Step 3 — Upload¶

    Press Continue. The upload shows in three phases — Set up Trapper, Send the images (with a bar, the amount sent and the time left) and Trapper processes them, which happens on TRAPPER's side and needs no waiting — and, under them, how many deployments and images have been sent and a row for each deployment with its state. A deployment's steps (connect, classification, location, deployment, package, csv, upload, process, wait) are each marked as running, done or skipped. The steps that made or found something in TRAPPER — the location, the deployment and, at the end, the collection — show a link to its page in TRAPPER (for example https://trapper.example.org/geomap/deployment/detail/47/), to check there that it was created or updated. A dry run links to what is already there; what it would create has no page yet. Stop ends it — what is already in TRAPPER stays there. When one fails, the others go on, and the summary says so: "1 deployment uploaded, 1 could not be uploaded." The failed one is in the list with its reason — when TRAPPER refuses a deployment because its location belongs to someone else, the reason says who owns it. The page shows the date of the run and a Download report link: the report of the upload is kept with the others (Settings › Reports), a row per deployment and step. Upload more starts over.

    The zips and yamls are written under <data folder>/packages/<research project>/. A deployment that was uploaded gets an upload.json, which is what the list uses to say so.

    9. Utils¶

    Press 🧰 Utils, under the task cards of the menu. It holds the maintenance tasks of the local collections; pick one, and Back returns to the list.

    Check and fix dates and times¶

    For the images of a card copied to a folder whose camera clock went wrong — it was reset, or it was never set — and whose dates are not the days they were taken. It works on the copy, never on the card. It has a short head with a Help button that explains each option, and five steps; the last four are locked until the dates are checked.

    1. Choose the folder and the visit. The folder (Browse… or type it), then the revision and, among its visits, the visit that left the camera. The research project is the default one, the one in the card at the top right. The visit is optional: without it the time jumps are found, but the dates cannot be checked against a period. With it, the period is the one of the deployment: from that visit to the next one at the site that collected the card, with a margin of a few hours. Press Check the dates.
    2. Check the dates. The images are read in the order the camera numbered them and split into segments: a segment is a run of consecutive images taken with the clock in one setting, and a new one starts wherever the time goes backwards from one image to the next. You see the number of images, the period, the segments and how many images are outside it, a chart, the problems found (images with no date, jumps, images outside the period) and each segment with its state — In its period, Partly outside or Outside its period.
    3. Fix the segments. For each segment that is not in its period you choose what to do with its images: move them into the period — the shift is shown and asked before it is made — or remove them. The shift suggested takes the first segment to start when the deployment started, and each later one to go on from where the one before ended. The images with no date can only be removed.
    4. Fix the dates. To shift by hand any run of images — even one — from an image to another, by an offset (forward or back, in days, hours, minutes and seconds) or from an image whose real time you know. The reason is written down with the fix.
    5. Fixes made. What was done, in order, with the day, who and why.

    Every change is made on the images of the folder — a shift rewrites their dates with ExifTool, which is needed — and no second copy is kept: each fix is written down in time_corrections.json, in the folder, so a shift is undone by shifting back by the same amount. After each fix the folder is read again, so the segments, the problems and the suggestions are those of the images as they are now: two segments that were fixed so that they follow each other become one. Removed images are deleted and cannot be put back.

    Sync local collections¶

    Press 🔄 Sync local collections. Use it when TRAPPER already has deployments that the collections folder doesn't — say, imported years ago, or from another computer — so that the statistics of the next revisions can compare with them, and the folder reflects what TRAPPER holds.

    1. Pick a research project, then one of its classification projects.
    2. Pick a collection (those of the classification project whose name starts with R) and, under it, the deployments to sync — with Select all.
    3. Tick Also download the images from Trapper if you want them too (see below).
    4. Press Sync.

    What is missing is created, one deployment at a time, and a live log says what is happening:

    • the research project (research_project.json) and its locations.json;
    • the collection (with its collection.json and <collection>_FileTimestampLog.csv);
    • each chosen deployment's deployment.json, in the collection its id starts with, and an images.json made from what TRAPPER holds for its images (names, when they were taken, observations).

    What is already in the folder is left as it is, whatever TRAPPER says. Nothing is changed in TRAPPER, and no image is downloaded unless you ask for it — so there is no preprocessing.json, and the size, pixels and hashes are missing from images.json, which is marked "source": "trapper". A deployment synced this way is read-only for the app: what TRAPPER holds isn't modified here. New locations synced from TRAPPER are pending until a visit starts them; the status of an existing location is left unchanged.

    Downloading the images¶

    With Also download the images from Trapper ticked, each chosen deployment's images are also downloaded, four at a time, into its folder — named as TRAPPER names them (R0003-DONA_01__20240901_1.JPEG), the file TRAPPER holds. A deployment can have thousands of images, so it can take long and need a lot of disk space. The log says how far each deployment is.

    • The files come through the classification project you picked: TRAPPER only gives the access token of a file — private ones too, for an account that can see them — in the media of a classification project, so an image that isn't in a collection of that project can't be downloaded. The result says how many of each deployment weren't.
    • What is already in the folder is kept, so syncing again completes a download that was stopped, or retries the images that failed. A file is written under a temporary name and moved into place when whole: a stop never leaves half an image.
    • The deployment is still a synced one: its images aren't preprocessed, renamed or sealed, so it can't be uploaded or repaired from here.

    The result lists, per kind, what was created and what was already there, the deployments no collection of the classification project claims, and any that TRAPPER holds in a way that isn't a valid deployment — with the reason — and were left out.

    Repair local deployments¶

    Press 🛠️ Repair local deployments. Use it when a deployment of the collections folder has lost its metadata files, or its images were touched — so it no longer matches its seal — and you want it back in working order.

    1. Pick a research project and one of its collections, both from the collections folder.
    2. Press Check the deployments. A deployment is valid if its seal.json still matches it: every image and its deployment.json are as they were sealed. Anything else — no seal, changed or missing images, a missing or unreadable metadata file — is not valid, and the table says what is wrong. A deployment synced from TRAPPER is not touched.
    3. The ones that are not valid start ticked (Select all, Select the not valid and Select none change it). Press Repair.

    Each deployment is repaired in turn, with its steps shown:

    • Dates. The capture date of every image is read from its EXIF, as the camera's wall clock, and the deployment's period is decided: if the collection's <collection>_FileTimestampLog.csv has a row for it, the log says it, whatever the images say; otherwise the period is the one the deployment.json that is left has, or else the one of the images, and the row is added to the log. The log itself is never rewritten but to add that row.
    • deployment.json — what is left of it, plus the location's details (name, coordinates), the camera of the images, and the period. If something required can't be known — the location has no coordinates, say — the repair stops and says so.
    • preprocessing.json and images.json — one entry for every image in the folder, with its date, hashes, camera and size. What can't be known is left empty: the original name of a renamed image, unless an earlier preprocessing.json says it, and the hash of the original, unless the image's XMP metadata does.
    • seal.json — the images are validated and postvalidated again, as in the wizard, and sealed with the result (marked as recovered). A deployment is sealed even if its images fail a check: the report says which.

    A report is written, and shown, with what was written and what the images passed — and four checks of the preprocessing the folder can answer: the names (<DEPLOYMENT>__<YYYYMMDD>_<n>.<EXT>, with the day of the capture date and each number once), the size (not wider than the width of the settings), the XMP metadata (needs ExifTool) and that the images are still the ones that were preprocessed. What the preprocessing did — the resizing, the renaming — can't be checked beyond that: the originals are gone.

    Backup and restore¶

    Press 🧰 Utils, then Backup and restore. It keeps the settings and the data of a research project in one .zip file, and puts back what a file holds. It asks first whether to make a backup or to restore one.

    Making a backup. It asks:

    1. What to back up. The global settings (a check, on by default; without passwords or secrets, and without the folders of this computer) and a research project (the active one comes chosen; leave it empty to back up only the settings). Of the project: its data (the research project, locations, cameras and SD cards), the list of visits, and the deployments — each one, a whole revision, or all — with their size. A switch, Include the images of the deployments, says whether their images go in (off by default) and how many megabytes that adds.
    2. Where to keep it. A folder. The file is named after what it holds and the day (wildintel-backup_DONA_20261030-103000.zip), and a bar shows the progress. When it is made, it says what the file holds and offers to open the folder.

    Restoring. It asks for the backup file, and shows what it says it holds (when it was made, by which version, of which project, and the list), and what of it is already here. You pick what to restore: the settings, the data of the project, the visits and the deployments, and — if the backup has them — their images. Replace what is already here is off by default: what is there is left as it is and only what is missing is added; on, what the backup holds wins. What is archived stays archived whatever is chosen (an archived location, camera or SD card never goes back). Restoring the settings keeps the passwords and the folders of this computer.

    10. Troubleshooting¶

    "Backend not reachable — is the server running?"
    The red bar at the top. The window that started the app was closed, or it crashed. Start the app again, and look at the log (Settings › General) if it recurs.
    The browser doesn't open
    Open http://127.0.0.1:8769 yourself. If that port was busy the app took the next free one: the window that started it says which (Server on http://127.0.0.1:8770).
    "Incorrect Trapper username or password"
    The username is the email of your account. Check it in Settings › Uploader › Trapper and press Test connection.
    "Could not connect to the Trapper server"
    The URL is wrong — it needs https:// and no trailing path — or the server is down or unreachable from your network.
    The metadata step is greyed out: "ExifTool is not installed"
    The downloadable app ships its own ExifTool. Running from the source code, install it (sudo apt install libimage-exiftool-perl, brew install exiftool) — or switch the step off.
    "This deployment already exists"
    A deployment with that id is already kept in the collections folder. Choose another revision or location, or move that folder away; importing would otherwise mix two sets of images.
    A location has no timezone
    Added by hand without one, or synced from a TRAPPER location that has none. Edit it in the Origin step; the app won't guess it.
    "Not preprocessed — import it again through the wizard"
    The deployment has no preprocessing.json: it was copied by hand, or synced from TRAPPER (which already has its images). Only deployments imported with the wizard can be uploaded.
    The upload says TRAPPER refuses the package
    TRAPPER checks the package's timezone and summer-time setting against the location's. If you changed them for the location in TRAPPER, they must be the same here — edit the location in the Origin step.
    The upload fails with "Trapper's uploader accepted the login but gave no session"
    The uploader's login answered without the session it should hand out. The message includes what Trapper said: send it to the Trapper administrator, or attach it to a bug report.
    Files ending in _exiftool_tmp in a deployment's folder
    ExifTool writes the metadata of each image through a temporary file; one it was interrupted in (the app stopped in the middle of an import) is left behind. The app removes them when the metadata step ends, or fails, but not if it was killed: delete them, and import again.
    An image was skipped
    The import lists skipped images with the reason, and goes on with the rest. A corrupted file is the usual cause; the Corrupted images validation finds them before importing.
    Reporting a problem
    Set the log level to DEBUG (Settings › General), repeat the steps and attach the log file to the report at github.com/wildintelproject/wildintel-uploader/issues.
